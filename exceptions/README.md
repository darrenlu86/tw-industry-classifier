# 本地例外表

**這個目錄的 `local_exceptions.json` 不進版控**（見 `.gitignore`）。

## 這張表在整套流程裡的位置

先講清楚它**不是**什麼：分類 pipeline 對未來的新客戶**不依賴人工裁決**。
丟一個沒看過的統編進來，答案由官方名冊、稅籍碼與名稱規則決定，例外表是空的也照樣跑。

它是什麼：**回溯既有名單時留下的一次性裁決紀錄**。整理一批存量資料時，
總會遇到帳務系統的佔位碼、已經解散但仍在名單裡的舊戶、或是官方名冊分類與
自己業務口徑不同的個案。當時查證的結論記在這裡，下次重跑同一批名單才不用重查、
也才看得出當初為什麼那樣判。

所以它會隨存量名單一起長，不會隨新客戶一起長。空的例外表不是待辦事項。

## 為什麼要分開放

`core/rules.py` 放的是通用規則——稅籍碼表、值域、名稱關鍵字，對任何人都適用。

但實務上一定會有「這家機構我們就是要歸在某一類」的人工裁決，理由通常涉及
業務往來關係、對特定公司的內部研究、或帳務系統的歷史包袱。這類內容不該混進通用規則：

- 混在一起會讓規則檔看起來像一份客戶清單
- 一個統編出現在「我們為它建了例外」的表裡，等於間接揭露它是誰的處理對象
- 換一個組織使用時本來就該重新檢視，不該照抄別人的裁決

## 怎麼用

```bash
cp exceptions/local_exceptions.example.json exceptions/local_exceptions.json
# 編輯 local_exceptions.json，填入你的裁決
py -3.12 classify.py --doctor        # 會顯示載入了幾筆
```

檔案不存在時所有表都是空的，分類器照樣跑——只是少了那些人工裁決，
該類統編會退到後面的規則層（通常是稅籍碼表或名稱關鍵字）。

## 各張表

### `tax_id_fix` — 統編歸戶（查詢重導向）

`{ 帳務端使用的統編: [實際要查的統編, 理由] }`

用途：帳務系統常見用 `00000000` 之類的佔位碼給沒有公司登記統編的單位
（政府機關、部分法人）；也常見同一實體有兩個統編（境外母公司與台灣辦事處、
舊統編與現行統編）。查到實際該查的統編後填在這裡。

**這是查詢重導向，不是改寫**（2026-08-21 語意定版）：

| 欄位 | 值 |
|---|---|
| `統一編號` | **輸入原值**（帳務端的那一個），不改寫 |
| 名稱、分類、依據 | 依**修正統編**的查詢結果（名冊／稅籍／上市櫃／GCIS／名稱解析全部用它查） |
| `統編備註` | `統編歸戶：查詢採 <修正統編>（<理由第一段>）`；既有備註以 `；` 串接 |

為什麼輸出鍵不改寫：分類結果要 join 回原始帳務報表。改寫鍵會讓原鍵直接消失、
整條鏈斷掉——同一實體有兩個統編時，**戶鍵由你決定，這個工具不替你決定**。
（v4 至今輸入 A 會輸出成 B，屬既有缺陷，2026-08-21 一併修正。）

批次裡同時有 A 與 B 兩列時，兩列都會保留、各自輸出自己的鍵，分類結果相同。

⚠️ **這張表是別名歸戶，只對你自己那套帳務資料成立**。
「佔位碼 `00000000` 就是某個機關」這種對應，是從某一份資料集的上下文查證出來的；
換一份資料集、換一個來源系統，同一個佔位碼可能對到完全不同的單位，甚至根本沒有對應。
**換資料集必須重新檢視整張表**，不要照抄。

### `override` — 已裁決例外

`{ 統編: [大分類, 子分類, 理由, 裁決日] }`

用途：名冊或稅籍碼的判定與事實不符時。**理由必填**，而且要寫得讓三個月後的人看得懂——
季度複核時只會看這張表，判斷「事實有沒有變」（併購、更名、法規變動）。

#### 兩種值形態

**(A) 身分軌值**（原有形態）：大分類 ∈ `GROUPS`、子分類 ∈ `SUBGROUPS`。
判定結果照填，單軌的產業大類／產業子類沿用同一組值。

```json
"12345678": ["證券期貨", "證券商", "業務往來主體為其證券子公司", "2026-01-01"]
```

三種典型情況：

| 情況 | 例子 |
|---|---|
| 稅籍碼不反映本業 | 消費分期業者的稅籍主碼登記成批發業 |
| 官方名冊的分類與業務口徑不同 | 金控依名冊歸銀行端，但實際往來主體是證券子公司 |
| 行政法人 | 稅籍是研究服務業，但受政府監督 |

**(B) 行業軌值**（2026-08-21 新增）：大分類填 **A–S 十九大類字串**
（逐字取自 `rules.py` 的 `SECTION_RANGES`，例如 `"C 製造業"`）或單軌專屬值 `"其他"`。

```json
"23456789": ["C 製造業", "26 電子零組件製造", "人工查證：實際從事印刷電路板製造", "2026-08-21"]
```

- 單軌的產業大類／產業子類直接採用該值；**子分類不受 `SUBGROUPS` 限制**，
  可以是任意描述字串或留空
- 身分軌（輸出的「大分類（僅供參考）／子分類（僅供參考）」）自動降為
  `一般企業／未細分`，值域自我檢查照樣通過
- 依據層 `L1 特殊規則`、判定規則 `L1-3`、信心 `high`
- **大類字串必須逐字合法**。打錯字（例如 `"C製造業"` 少一個空格）不會報錯，
  會被當成身分軌值處理，然後在批次的值域自我檢查裡以「越界」現形
- **登記狀態若為解散類，L3-D 仍會覆寫成「已解散（歷史戶）」**（信心降 `low`）。
  「已解散」回答的是「這家還在不在」，與產業是人工填的還是引擎判的無關——
  兩種值形態在這件事上一致。裁決本身不會消失，仍在判定規則裡看得到

> ⚠️ **形態 (B) 只該用在官方來源全查無的戶。**
> 這是替「稅籍、各名冊、上市櫃、GCIS 都答不出來」的戶填空白用的——人工逐戶查證的
> 結果總得有地方放。**對有稅籍的戶填行業軌值會直接蓋掉稅籍主碼的判定**：
> L1 是最先命中的一層，機制上不擋，靠的是紀律。
>
> 2026-08-11 曾定版「行業軌禁止人工覆寫」，使用者 2026-08-21 指示放寬到上述範圍。
> 放寬的是「查無時可以填」，不是「可以改寫查得到的」。填之前先確認那一戶
> 真的四個來源都查無（跑一次 `classify.py <統編>` 看產業大類是不是
> 「未登記（稅籍查無）」）。

### `frozen_names` — 存量凍結官方名稱

`{ 統編: [官方名稱, 查證來源] }`

用途：四個官方名冊都查無名稱時（已解散公司、外商在台、機關名冊未收錄的機關），
人工查證一次後凍結。**請把查證來源寫清楚**，否則將來沒人知道這個名稱是哪來的。

### `frozen_status` — 存量凍結登記狀態

`{ 統編: "登記狀態" }`

用途：標記已知終止登記者（合併解散、廢止、解散已清算完結）。
填了之後該筆的 `信心` 會被降為 `low`，進季度複核清單。

### `peripheral_extra` — 追加周邊單位

`{ 統編: [官方名稱, 所屬大類] }`

`core/exceptions.py` 已內建 7 家法定金融市場基礎設施（證交所、集保、期交所、
櫃買中心、碳權交易所→證券期貨；票交所、聯徵中心→金控與銀行）。
如果你的組織把其他公設機構或公協會也視為周邊單位，加在這裡。

判定結果＝`所屬大類／周邊單位`；所屬大類限「金控與銀行／證券期貨／保險」
（v4 起周邊單位不再歸政府機關，改掛所服務的金融市場大類）。

### `no_taxid_accounts` — 無統編歸戶表（v5）

`{ 官方名稱: [大分類, 子分類, 理由] }`

用途：統一編號欄整格空白的帳。實務上一定會有——政府單位的分支、
沒有台灣登記的合作對象、帳務系統建檔時就沒填的舊戶。

引擎的 L0-N 用**名稱完全比對**查這張表：命中就依表值定案，查無就歸「無法分類」。
之所以要求完全比對，是因為名稱是這張表唯一的鍵，模糊比對只會製造難查的錯配——
與其猜一個看起來像的，不如明白說「查無」。

比對前只做「去頭尾空白」一項正規化。所以請把名稱寫成**與輸入檔逐字相同**的樣子，
包含全形括號、「股份有限公司」有沒有寫全、中間有沒有空格。

大分類與子分類同樣受 `core/rules.py` 的 `SUBGROUPS` 值域約束。

## 維護原則

1. **每筆都要有理由與日期**。沒理由的裁決三個月後就變成沒人敢動的黑盒。
2. **不要用裁決掩蓋規則問題**。如果同一種情況要加第三筆裁決，那應該改 `rules.py` 的規則，
   而不是繼續累積例外。這條是本表不會無限膨脹的原因。
3. **不必為了新客戶預先建表**。新統編走官方名冊與稅籍碼就有答案；
   只有在回溯既有名單、遇到官方資料答不出來的個案時才記一筆。
4. **存量裁決要定期回頭看**。已經記在表裡的條目適用季度複核（連同輸出 `信心=low` 的列）——
   併購、更名、法規變動都會讓當初的裁決失效。這是針對**存量**的紀律，
   不是說每季都得補新條目。
